# RebarOptima: Complete Repository & Architectural Audit
**System:** RebarOptima Construction Management SaaS Platform  
**Audit Date:** November 2026  
**Status:** Audit Complete (Strictly Inspection & Documentation — No Code Modified)  
**Lead Auditor:** Principal Software Architect, Senior Full-Stack Engineer & Security Auditor

---

## 1. Executive Summary

A comprehensive, non-destructive audit was performed across the entire RebarOptima repository, covering all **439 application source files**, **32 major modules**, database schemas, infrastructure configurations, and engineering calculations.

RebarOptima contains impressive domain capabilities — including 1D Cutting Stock Optimization, Bar Bending Schedule (BBS) generation, Concrete Casting batch tracking, and real-time project collaboration. However, the application exhibits significant architectural debt resulting from high-velocity feature additions:
1. **Split-Brain Backend:** The server runtime executes as an Express monolith in `main.ts`, while dozens of NestJS controllers exist as dead code.
2. **Critical Production Risks (P0):** Silent failover to in-memory storage on database connection drop, hardcoded fallback JWT secrets, and destructive batch deletion without stock rollback.
3. **Multi-Layer Duplication:** Fragmented block/wing entities across 5 collections, dual competing BBS implementations, and duplicate business logic.
4. **Testing Deficit:** Complete absence of frontend automated tests (0% coverage) and zero unit tests for the core cutting stock optimizer or BBS bend deduction math.

## 5. Top 10 Critical Issues (Ranked)

1. **REB-P0-002 (Silent In-Memory Fallback):** On database timeout, `main.ts` silently switches to in-memory arrays. Next restart permanently wipes all newly created data.
2. **REB-P0-004 (Hardcoded JWT Secret):** `main.ts` uses fallback `'fallback-access-secret'`, allowing trivial token forgery and unauthorized superadmin access.
3. **REB-P0-005 (Destructive Batch Deletion):** Deleting a batch removes the record but leaves stock permanently deducted and phantom remnants in inventory.
4. **REB-P0-006 (False-Positive Health Probe):** `/api/health` returns HTTP 200 OK even while running in disconnected in-memory mode, keeping broken instances in service.
5. **REB-P0-003 (Docker-Compose Env Mismatch):** `docker-compose.yml` provides `DATABASE_URL` instead of `MONGODB_URI`, triggering in-memory fallback on initial container launch.
6. **REB-P1-004 (Missing Transaction Rollbacks):** Multi-collection inventory and batch deductions lack MongoDB multi-document session rollbacks, risking partial writes.
7. **REB-P1-015 (Optimizer Event-Loop Lockup):** Synchronous 1D-CSP solver blocks the Node.js event loop for 10–30s on large cut lists, dropping HTTP requests and WebSocket connections.
8. **REB-P1-012 (Optimizer Kerf Overcounting):** Kerf loss is applied to $N$ parts instead of $N-1$ cuts, causing inaccurate waste estimates and rejecting valid cutting patterns.
9. **REB-P1-003 (Divergent Project Keys):** `localStorage` uses both `'selectedProjectId'` and `'rebar_active_project_id'`, causing stale project data after switching projects in the navigation bar.
10. **REB-P1-008 (Wildcard CORS):** Unrestricted `Access-Control-Allow-Origin: *` leaves authenticated sessions exposed to cross-origin abuse.

## 6. Top 10 Architectural Problems

1. **Split-Brain Backend:** Express runtime vs unused NestJS controllers, creating confusion and dead code.
2. **Monolithic `main.ts`:** 3,466 lines combining database setup, middleware, inlined business logic, and WebSockets.
3. **Vue 3 Contamination in React 19:** Full secondary framework (`vue`, `element-plus`, `vueuse`) bundled into a React application.
4. **Quadruplicate Block Collections:** 5 separate collections storing block/wing entities with divergent schemas.
5. **Dual BBS Implementations:** Legacy `BBSPage.jsx` and Phase 2 `BBSWizard.jsx` operating concurrently with divergent formulas.
6. **Triple Inventory Silos:** Steel inventory, general site inventory, and casting materials operate as disconnected modules.
7. **Monolithic Frontend Routing:** 170-line ternary routing tree in `App.jsx` lacking route-based code splitting.
8. **Fragmented Reporting Engines:** 4 PDF generators and 2 Excel exporters with divergent styling and page logic.
9. **Inconsistent Entity Identifiers:** Mix of BSON `ObjectId` and plain hex strings requiring repetitive `$or` query blocks.
10. **Double Database Lookups per Request:** `resolveUserAndCompany` executes 2 sequential DB queries on every authenticated API call.

---

## 7. Top 10 Duplication Problems

1. **Block/Wing Data Storage:** Stored in `project_blocks`, `casting_blocks`, `bbs_blocks`, `crm_blocks`, and `blockwings`.
2. **Bar Bending Schedule Suites:** Dual UI pages and dual API route sets for BBS.
3. **Cutting Batch Logic:** `batches.service.ts` completely duplicates inline batch logic in `main.ts`.
4. **PDF Generation Pipelines:** `html2pdf.js`, `jspdf`, `pdfkit`, and custom canvas export pipelines exist in parallel.
5. **Excel Export Implementations:** Frontend `xlsx` export vs backend `ExcelJS` generation.
6. **Activity & Audit Logs:** Project activity logs, drawing activity logs, and central activity logs operate on separate collections.
7. **Project Header Resolvers:** Repeated project verification logic across controllers rather than central middleware.
8. **Steel Ledger Records:** Parallel ledger entries in `steel_ledger` and `inventory_transactions`.
9. **Status Badge Components:** Multiple independent status badge implementations across dashboard tables.
10. **Root vs Workspace Dependencies:** Redundant declarations of 6 packages in both root and frontend `package.json`.

---

## 8. Top 10 Production Risks

1. **Permanent Data Loss:** Ephemeral in-memory fallback on database connection dropout.
2. **Load Balancer Failure Detection Failure:** `/api/health` returns 200 OK when database is dead.
3. **Container Boot into Memory:** Docker Compose uses `DATABASE_URL` which `main.ts` ignores.
4. **Unauthenticated Access:** Trivial JWT token forgery via hardcoded fallback secret.
5. **Server Freeze on Optimization:** Single-threaded optimizer blocks event loop, freezing entire API.
6. **Partial Write Inconsistencies:** Lack of atomic multi-document transaction rollbacks.
7. **Database Memory Exhaustion:** Unbounded `.find({}).toArray()` queries on large collections.
8. **Cross-Tenant Data Tampering:** Ingestion of untrusted `req.body.companyId` on certain POST endpoints.
9. **Zero Frontend Regression Safety:** Absence of automated tests makes any UI refactoring high risk.
10. **Stale Data on Site:** Workers viewing stale project data due to local storage key desynchronization.

## 9. Recommended Implementation Sequence

```
Phase 1 (Week 1): Immediate P0 Stabilization
  1. Remove InMemoryDb; fail-fast with process termination.
  2. Align Docker Compose to MONGODB_URI.
  3. Enforce JWT_ACCESS_SECRET injection.
  4. Fix batch deletion inventory rollback compensation.
  5. Correct optimizer kerf calculation formula.

Phase 2 (Weeks 2–3): Database & Context Integrity
  1. Standardize BSON ObjectId lookups.
  2. Create compound indexes for attendance and inventory.
  3. Synchronize project context epoch across all frontend submodules.
  4. Offload cutting optimizer to Worker Threads.

Phase 3 (Weeks 4–5): Consolidation & Decoupling
  1. Retire legacy BBSPage in favor of Phase 2 BBS Wizard.
  2. Migrate duplicate block collections into canonical project_blocks.
  3. Extract inlined routes from main.ts into dedicated router modules.
  4. Evict Vue 3 / Element Plus and dead NestJS packages.

Phase 4 (Weeks 6–7): Modernization & Production Readiness
  1. Implement React.lazy route chunking.
  2. Establish Vitest frontend test harness.
  3. Wire up accurate HTTP 503 health probes and structured logging.
```
