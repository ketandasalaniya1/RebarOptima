**Status:** Audit Only — No Code Modifications

## 1. Executive Summary

A comprehensive architectural inspection of the RebarOptima repository reveals a **critical split-brain runtime architecture** between an abandoned/unmounted NestJS module structure and an active monolithic Express/MongoDB implementation.

The repository contains 439 active source files across a monorepo-style single repository holding both `/frontend` (React 19 + Vite) and `/backend` (Express + Socket.IO with dead NestJS scaffolding).

## 3. Runtime Architecture & The "Split-Brain" Finding

### Issue ID: REB-P0-001
- **Severity:** P0 (Critical Architectural Integrity)
- **Category:** Architecture / Backend
- **Affected Files:**
  - `backend/src/main.ts`
  - `backend/src/app.module.ts`
  - `backend/package.json`
  - `backend/src/projects/projects.controller.ts` vs `backend/src/projects/projects.routes.ts`
  - `backend/src/batches/batches.controller.ts` vs `backend/src/main.ts`
  - `backend/src/inventory/inventory.controller.ts` vs `backend/src/main.ts`
- **Evidence:**
  `backend/package.json` specifies `"start": "node dist/main"` and `"dev": "nest start --watch"`. However, inside `backend/src/main.ts`:
  ```typescript
  // Line 51:
  const app = express();
  // ... 3,400 lines of inline Express endpoints and routers ...
  const httpServer = createServer(app);
  httpServer.listen(PORT, () => console.log(`🚀 Express server with Socket.IO listening on port ${PORT}`));
  ```
  `NestFactory.create(AppModule)` is **never invoked anywhere** in the repository.
- **Problem:**
  The project presents itself as a NestJS enterprise application with NestJS CLI configs, `@nestjs/*` dependencies, `@Injectable()` services, `@Controller()` classes, and Mongoose `@Schema()` definitions. In reality, the runtime is a pure Express 5 application running on `main.ts`. Developers modifying NestJS controllers or services in `projects/`, `inventory/`, `batches/`, `users/`, and `auth/` are modifying **dead code** that has zero effect on runtime behavior.
- **Impact:**
  - High risk of development desynchronization (fixing a bug in `batches.service.ts` leaves the production bug active in `main.ts`).
  - Misleading documentation and developer onboarding failure.
  - Bloated bundle and memory usage with unneeded NestJS frameworks loaded into memory.
- **Recommendation:**
  Either complete the migration to NestJS by bootstrapping `AppModule` via `NestFactory.create()` and mounting existing Express routers as Nest middleware/controllers, OR explicitly remove the unused NestJS scaffolding, consolidating all business services into a clean, modular Express architecture.

## 4. Database Connection & In-Memory Fallback Danger

### Issue ID: REB-P0-002
- **Severity:** P0 (Critical Data Loss & Integrity Risk)
- **Category:** Database / Backend
- **Affected Files:**
  - `backend/src/main.ts` (lines 76–320)
  - `backend/src/db.ts`
- **Evidence:**
  In `main.ts` lines 311–320:
  ```typescript
  } catch (err: any) {
    console.warn('⚠️ Could not connect to MONGODB_URI. Falling back to In-Memory DB:', err.message);
  }

  if (!isInMemoryActive) {
    console.warn('⚠️ MongoDB Atlas is not accessible. Using clean In-Memory DB (No test/default data created).');
    isInMemoryActive = true;
    db = memoryDbInstance as any;
  }
  ```
  An entire custom `InMemoryDb` class with `InMemoryCollection` is implemented in `main.ts` (lines 112–273).
- **Problem:**
  If MongoDB Atlas experiences a network hiccup, DNS resolution failure, or connection timeout during startup, the production server silently falls back to an in-memory JavaScript array store.
- **Impact:**
  - End users and site engineers can create batches, input inventory, record attendance, and spend petty cash while believing data is being safely saved.
  - Upon the next container restart, dyno sleep, or server reboot, **100% of newly entered data is permanently lost without a trace**.
  - Multi-tenant tenant separation is compromised because `InMemoryCollection` lacks proper indexing and transaction support.
- **Recommendation:**
  Fail-fast in production. If `MONGODB_URI` connection fails, log a critical error and terminate the process with non-zero exit code (`process.exit(1)`) so orchestrators (Docker, Kubernetes, PM2, ECS) restart or alert the operations team. Never silently swallow connection errors with in-memory storage in production SaaS environments.

## 5. Frontend Framework Contamination

### Issue ID: REB-P2-001
- **Severity:** P2 (Medium Architecture Issue)
- **Category:** Architecture / Frontend / Dependencies
- **Affected Files:**
  - `frontend/package.json`
  - `frontend/src/pages/DrawingsPage/components/CADViewer.jsx`
- **Evidence:**
  `frontend/package.json` lists React 19 alongside Vue 3 and Element Plus:
  ```json
  "dependencies": {
    "vue": "^3.5.44",
    "element-plus": "^2.14.7",
    "vue-i18n": "^11.4.16",
    "@vueuse/core": "^11.1.0",
    "react": "^19.2.7",
    "react-dom": "^19.2.7"
  }
  ```
  In `frontend/src/pages/DrawingsPage/components/CADViewer.jsx`:
  ```javascript
  import { createApp, h, shallowReactive } from 'vue';
  ```
- **Problem:**
  A React 19 SPA is embedding a secondary Vue 3 runtime instance inside a React component to host the `@mlightcad` drawing viewer.
- **Impact:**
  - Significantly increases initial bundle size (loading both React and Vue runtimes plus Element Plus styling).
  - Potential CSS conflicts between Element Plus and global Vanilla CSS design tokens.
  - Increases attack surface and dependency maintenance overhead.
- **Recommendation:**
  Wrap the `@mlightcad` vanilla JS WebGL canvas directly using a native React `useRef` lifecycle hook, removing Vue 3, Vue-i18n, VueUse, and Element-Plus from the application bundle entirely.
