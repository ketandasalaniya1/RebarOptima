# 04. BACKEND CODE & API ARCHITECTURE AUDIT
**Project:** RebarOptima SaaS  
**Audit Date:** November 2026  
**Auditor:** Principal Backend & Distributed Systems Architect  
**Status:** Audit Only — No Code Modifications

---

## 1. Executive Summary

The RebarOptima backend exhibits significant architectural disparity. While modern enterprise features (like multi-tenant role-based access, Socket.IO project chat, and geofenced attendance) have been implemented, the codebase suffers from:
1. **The 3,466-line `main.ts` monolith**, which contains thousands of lines of business logic, database queries, and custom in-memory mock storage.
2. **Dual-driver database fragmentation**, mixing MongoDB native driver (`MongoClient`) with dormant or isolated Mongoose models.
3. **Missing transaction guarantees** on critical inventory deductions and financial ledgers.
4. **Inconsistent API response schemas** and error envelopes across route handlers.

## 2. Detailed Backend Findings

### Issue ID: REB-P0-003
- **Severity:** P0 (Critical Architecture & Maintainability)
- **Category:** Backend / Code Architecture
- **Affected Files:**
  - `backend/src/main.ts` (3,466 lines)
- **Evidence:**
  `main.ts` directly handles:
  - Express server bootstrapping and CORS headers (lines 51–61)
  - Custom in-memory database engine implementation (lines 76–275)
  - Database connection & default seed initialization (lines 280–320)
  - Role and subscription catalog definitions (lines 350–712)
  - JWT token generation & verification middleware (lines 715–745)
  - Route mounting for 15 submodule router factories (lines 746–770)
  - Developer console and multi-tenant billing APIs (lines 1350–1670)
  - Activity logs & CSV exports (lines 1680–1850)
  - User authentication (signup, signin, refresh) (lines 1851–2050)
  - Role management CRUD (lines 2100–2250)
  - User management CRUD (lines 2251–2500)
  - Steel Inventory & Inward Stock CRUD (lines 2720–2939)
  - Scrap Sales CRUD (lines 2940–3050)
  - Steel Cutting Optimization & Batch commitments (lines 3051–3350)
- **Problem:**
  The main entry point violates the Single Responsibility Principle on an extreme scale. Modifying an authentication function carries the risk of inadvertently breaking the cutting optimizer or the seed mechanism.
- **Impact:**
  - Extreme merge conflict risk during team development.
  - High risk of regression errors.
  - Slow IDE indexing and impossible automated unit testing of isolated handlers.
- **Recommendation:**
  Extract all inline route blocks into modular controller/service files:
  - `src/auth/auth.routes.ts`
  - `src/users/users.routes.ts`
  - `src/roles/roles.routes.ts`
  - `src/inventory/steel-inventory.routes.ts`
  - `src/batches/batches.routes.ts`
  - `src/developer-console/developer.routes.ts`

### Issue ID: REB-P1-004
- **Severity:** P1 (High Data Consistency Risk)
- **Category:** Backend / Database Consistency / Transactions
- **Affected Files:**
  - `backend/src/main.ts` (lines 3070–3150: `POST /api/batches`)
  - `backend/src/main.ts` (lines 2952–2989: `POST /api/inventory/scrapsales`)
  - `backend/src/petty-cash/petty-cash.routes.ts`
- **Evidence:**
  In `main.ts` line 3070 (`POST /api/batches`), a committed cutting batch performs sequential updates:
  1. Inserts the batch record into `db.collection('batches')`.
  2. Loops over used stock items and executes `stockitems.updateOne(...)` deductions.
  3. Inserts newly generated remnant stock into `stockitems`.
  4. Inserts multiple transactions into `inventory_transactions`.
  **None of these sequential writes are wrapped in a MongoDB ClientSession transaction (`client.startSession()`).**
- **Problem:**
  If step 2 succeeds (deducting stock) but step 3 or 4 fails (e.g., due to a unique constraint violation, network timeout, or memory exhaustion), the database is left in a corrupt state: stock has been deducted from inventory, but the batch record or remnant stock was never committed.
- **Impact:**
  Physical inventory counts on the construction site will diverge from system records, causing stock discrepancies and financial inaccuracies.
- **Recommendation:**
  Wrap all multi-collection write sequences in `session.withTransaction()` blocks with automatic rollback on error.

### Issue ID: REB-P2-004
- **Severity:** P2 (Medium)
- **Category:** Backend / Performance & Memory
- **Affected Files:**
  - `backend/src/main.ts` (lines 1682–1750: `GET /api/activity-logs`)
  - `backend/src/main.ts` (lines 2830–2855: `GET /api/inventory/ledger`)
  - `backend/src/petty-cash/petty-cash.routes.ts`
- **Evidence:**
  In `main.ts` line 2845:
  ```typescript
  const transactions = await db.collection('inventory_transactions').find(query).sort({ date: -1 }).toArray();
  ```
- **Problem:**
  Unbounded queries loading all records into Node.js process memory using `.toArray()` without pagination (`limit` / `skip`).
- **Impact:**
  As a project matures and accumulates tens of thousands of transactions, these queries will experience latency spikes and eventually trigger `JavaScript heap out of memory` crashes.
- **Recommendation:**
  Enforce mandatory pagination with default `limit: 50` and maximum `limit: 200` on all listing endpoints.
