# 06. DATABASE ARCHITECTURE & SCHEMA AUDIT
**Project:** RebarOptima SaaS  
**Audit Date:** November 2026  
**Auditor:** Principal Database Architect & Data Engineer  
**Status:** Audit Only — No Code Modifications

---

## 1. Executive Summary

RebarOptima utilizes **MongoDB** as its primary data store. The database layer exhibits high architectural fragmentation:
1. **Hybrid Native Driver / Mongoose Coexistence**: `main.ts` uses the native `mongodb` package (`MongoClient`), while `bbs.express.ts` maintains its own standalone `mongoose.connect()` call, and NestJS schemas in `projects/`, `inventory/`, and `batches/` are unmounted.
2. **Schema Inconsistency (BSON ObjectId vs String)**: Foreign keys (`companyId`, `projectId`, `userId`) are inconsistently stored as BSON `ObjectId` in some documents and plain 24-character hexadecimal `string` in others.
3. **Missing Critical Compound Indexes**: Queries filtering by `(companyId, projectId, createdAt)` perform unindexed collection scans (`COLLSCAN`).

## 2. Detailed Database Findings

### Issue ID: REB-P1-008
- **Severity:** P1 (High Data Consistency & Query Performance Risk)
- **Category:** Database / Type Consistency
- **Affected Collections:**
  - `stockitems`
  - `batches`
  - `projects`
  - `petty_cash_transactions`
  - `crm_leads`
  - `drawings`
- **Evidence:**
  In `main.ts` line 2732:
  ```typescript
  const companyClause = ObjectId.isValid(companyId) && String(companyId).length === 24
    ? { $or: [{ companyId: new ObjectId(companyId) }, { companyId: String(companyId) }] }
    : { companyId: String(companyId) };
  ```
  In `project-access.ts` line 36:
  ```typescript
  export function idQuery(id: string) {
    if (ObjectId.isValid(String(id)) && String(id).length === 24) {
      return { $or: [{ _id: new ObjectId(String(id)) }, { _id: String(id) }] };
    }
    return { _id: String(id) };
  }
  ```
- **Problem:**
  Because documents have been inserted over time with mixed formats (some via Mongoose casting to `ObjectId`, some via Express native driver as raw strings), queries must continually execute `$or` clauses over both types.
- **Impact:**
  - Queries using `$or` over different types cannot effectively utilize simple single-field indexes.
  - Potential cross-tenant data leakage if string-to-ObjectId conversion fails or matches unexpectedly.
- **Recommendation:**
  Execute a non-destructive data normalization migration that standardizes all foreign keys (`companyId`, `projectId`, `userId`) to BSON `ObjectId`.

### Issue ID: REB-P2-006
- **Severity:** P2 (Medium Performance Risk)
- **Category:** Database / Indexing
- **Affected Collections:**
  - `attendance_records` (scanned on every check-in and monthly report)
  - `inventory_transactions` (scanned for steel ledger)
  - `chat_messages` (scanned on every message load)
  - `activitylogs` (scanned on developer and admin audits)
- **Evidence:**
  In `main.ts`, indexes are created only for basic seed collections. Missing compound indexes:
  - `attendance_records`: `{ companyId: 1, projectId: 1, date: 1, workerId: 1 }`
  - `inventory_transactions`: `{ companyId: 1, projectId: 1, date: -1 }`
  - `chat_messages`: `{ conversationId: 1, createdAt: 1 }`
  - `drawing_revisions`: `{ drawingId: 1, revisionNumber: -1 }`
- **Problem:**
  As collections grow past 10,000 records, queries without compound indexes result in CPU-intensive collection scans.
- **Impact:**
  Increased MongoDB Atlas query latency, potential connection timeouts, and degraded user experience.
- **Recommendation:**
  Define explicit, tenant-scoped compound indexes on startup across all core operational collections.
