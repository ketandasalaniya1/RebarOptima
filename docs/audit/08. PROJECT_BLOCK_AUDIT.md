# 08. PROJECT & BLOCK MANAGEMENT AUDIT
**Project:** RebarOptima SaaS  
**Audit Date:** November 2026  
**Auditor:** Principal Enterprise Architect  
**Status:** Audit Only — No Code Modifications

---

## 1. Executive Summary

Project-level scoping and Block/Wing hierarchical modeling are core requirements for multi-site construction ERPs. RebarOptima has established a robust **Project-First Access Control Gateway** (`project-access.ts`), but exhibits key inconsistencies in Block management and Geofence enforcement.

---

## 2. Detailed Findings

### Issue ID: REB-P1-011
- **Severity:** P1 (High Impact)
- **Category:** Architecture / Project Context
- **Affected Files:**
  - `frontend/src/store/slices/projectSlice.js`
  - `frontend/src/hooks/useActiveProject.js`
  - `frontend/src/utils/api.js` (lines 43–49)
  - `frontend/src/App.jsx` (lines 98–105)
- **Problem:**
  When a user switches projects via `ProjectSelector.jsx`, Redux updates `state.project.selectedProject` and writes to `localStorage['rebar_active_project_id']`. However, pages that use non-reactive local state or custom `useEffect` hooks without `selectedProject` in their dependency array continue displaying stale data from the previous project until manual page reload.
- **Impact:**
  Engineers may record an attendance log or commit a rebar cutting batch believing it belongs to the newly selected project when it is actually tagged with the previous project's ID.
- **Recommendation:**
  Ensure the active project context in Redux dispatches a global project epoch event (`projectEpoch`) that triggers cache invalidation or automatic refetching across all mounted sub-pages.

### Issue ID: REB-P2-007
- **Severity:** P2 (Medium)
- **Category:** Business Logic / Geofencing
- **Affected Files:**
  - `backend/src/attendance/attendance.service.ts`
  - `backend/src/projects/project.schema.ts` (lines 6–19)
  - `frontend/src/components/ProjectModals/GeofenceConfigModal.jsx`
- **Evidence:**
  `GeofenceConfigModal.jsx` allows users to configure both `circle` (center point + radius) and `polygon` (arbitrary GPS boundary points) geofences.
  However, in `attendance.service.ts`:
  ```typescript
  // Haversine formula calculation:
  const distanceMeters = calculateHaversineDistance(userLat, userLng, centerLat, centerLng);
  if (distanceMeters > geofence.radius) { ... }
  ```
- **Problem:**
  The backend attendance verification only evaluates circular radius distance. If an administrator creates a complex polygon geofence on a non-circular construction site, the backend **completely ignores the polygon vertices** and defaults to a radius or center check.
- **Impact:**
  Workers physically inside the polygon boundary (e.g., at the far end of an L-shaped construction site) may be falsely rejected as "Outside Geofence".
- **Recommendation:**
  Implement standard point-in-polygon (Ray Casting algorithm) checking in `attendance.service.ts` when `boundaryType === 'polygon'`.
