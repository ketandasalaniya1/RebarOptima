# 14. Dependency & Package Health Audit
**Project:** RebarOptima SaaS Platform  
**Audit Date:** November 2026  
**Auditor:** Principal Software Architect & DevOps Engineer  
**Scope:** Root, Frontend, and Backend `package.json`, dependency duplication, dead framework packages, version conflicts, security vulnerabilities, and bundle size footprint.

---

## 1. Executive Summary

The dependency architecture of RebarOptima displays severe structural anomalies stemming from incremental development without package hygiene:
1. **Dead Framework Bloat (Backend):** The backend installs 7 `@nestjs/*` framework dependencies (~120 MB in `node_modules`) despite the server executing as an Express monolith in `main.ts`.
2. **Framework Contamination (Frontend):** The frontend installs full **Vue 3, Element Plus, VueUse, and Vue-i18n** inside what is fundamentally a **React 19** single-page application.
3. **Workspace Version Collisions:** Packages such as `lucide-react` are declared at differing versions (`^1.25.0` in root vs `^1.23.0` in `frontend/package.json`).
4. **Duplicate Dependency Declarations:** Several 3D and CAD libraries (`three`, `@velipso/polybool`, `@mlightcad/mtext-*`) are redundantly installed both at the monorepo root and inside `frontend/package.json`.

## 3. High-Priority Dependency Issues

### 3.1 Dead NestJS Ecosystem in Backend
- **Affected Files:** `backend/package.json`
- **Packages:**
  - `@nestjs/common@^11.0.1`
  - `@nestjs/core@^11.0.1`
  - `@nestjs/mongoose@^11.0.4`
  - `@nestjs/platform-express@^11.0.1`
  - `@nestjs/cli@^11.0.0`
  - `@nestjs/schematics@^11.0.0`
  - `@nestjs/testing@^11.0.1`
- **Issue:** As established in `01. REPOSITORY_STRUCTURE_AUDIT.md`, `main.ts` instantiates standard Express via `const app = express()`. NestJS's dependency injection container, lifecycle hooks, and HTTP pipeline are never initialized.
- **Impact:**
  - ~120MB wasted disk space and container layer overhead.
  - Slower CI/CD dependency resolution during `npm install`.
  - Misleads developers into writing NestJS controllers that never respond to requests.

### 3.2 Vue 3 & Element Plus Contamination in React 19 Frontend
- **Affected Files:** `frontend/package.json`, `frontend/src/pages/BBSPage/CADViewer.jsx`
- **Packages:**
  - `vue@^3.5.44`
  - `element-plus@^2.14.7`
  - `@vueuse/core@^11.1.0`
  - `vue-i18n@^11.4.16`
- **Issue:** A React 19 application includes a complete secondary frontend framework (Vue 3) and an enterprise Vue UI component kit (Element Plus) solely because a legacy CAD viewer demo or third-party web worker wrapper copied Vue bindings.
- **Impact:**
  - Risk of Vue reactivity runtime polluting the global browser namespace.
  - Adds ~1.2MB of uncompressed JavaScript to the build artifacts.
  - Increases node_modules installation time significantly.

### 3.3 Root vs Workspace Redundant Declarations
- **Affected Files:** `package.json` vs `frontend/package.json`
- **Packages Declared in Both:**
  - `lucide-react`: `^1.25.0` (root) vs `^1.23.0` (frontend).
  - `three`: `^0.172.0` (root) vs `0.172.0` (frontend).
  - `@velipso/polybool`: `^1.1.1` (root) vs `^1.1.1` (frontend).
  - `@vercel/analytics`: `^2.0.1` (root) vs `^2.0.1` (frontend).
  - `@mlightcad/mtext-parser`: `^1.5.5` (root) vs `^1.5.5` (frontend).
  - `@mlightcad/mtext-renderer`: `0.13.4` (root) vs `0.13.4` (frontend).
- **Impact:** In npm workspace setups, declaring dependencies at root that are strictly consumed by a child workspace causes npm hoisting discrepancies, phantom dependency risks, and version divergence.

### 3.4 Duplicate Script in `backend/package.json`
- **Lines 10 & 13:**
  ```json
  "dev": "nest start --watch",
  "start": "node dist/main",
  "dev": "nest start --watch",
  ```
- **Issue:** Duplicate `"dev"` key in JSON file. While valid JSON parsers typically take the last key, it indicates poor file maintenance.

## 4. Security & Maintenance Risk Assessment

| Package | Category | Severity | Analysis & Risk |
|:---|:---|:---:|:---|
| `jsonwebtoken` (`^9.0.3`) | Backend Auth | **P1 (Security)** | Standard JWT library. Requires strict verification of `algorithms: ['HS256']` on every `jwt.verify` call to avoid algorithmic downgrade attacks. |
| `bcryptjs` (`^3.0.3`) | Backend Auth | **P2 (Perf)** | Pure JavaScript implementation of bcrypt. While memory-safe and zero-native-build, it is 3–5x slower than native C++ `bcrypt` under heavy authentication loads. |
| `html2pdf.js` (`^0.10.2`) | Frontend Export | **P2 (Maintenance)** | Relies on outdated versions of `jspdf` and `html2canvas`. Prone to CSS Grid/Flexbox rendering bugs and lack of PDF/A accessibility tags. |
| `pdfjs-dist` (`^6.4.299`) | Frontend Viewer | **P2 (Compatibility)** | Major version 6. Requires modern Web Worker configurations; Vite setup must pin worker asset loaders correctly to prevent CORS worker failures in production CDN environments. |
| `socket.io` & `socket.io-client` (`^4.8.4`) | Realtime | **Healthy** | Latest stable release. Compatible with bidirectional polling and WebSocket transport. |

## 5. Recommended Remediation Plan (Post-Audit)

1. **Step 1: Clean Up Dead NestJS Packages:** Once Express routing is officially standardized, remove `@nestjs/common`, `@nestjs/core`, `@nestjs/mongoose`, `@nestjs/platform-express`, `@nestjs/schematics`, `@nestjs/cli`, and `@nestjs/testing`.
2. **Step 2: Evict Vue from Frontend:** Inspect `CADViewer.jsx` and `@mlightcad` integrations, replace any residual Element Plus/Vue wrappers with native React 19 equivalents or plain DOM wrappers, and uninstall `vue`, `element-plus`, `@vueuse/core`, and `vue-i18n`.
3. **Step 3: Deduplicate Monorepo Root:** Remove `@mlightcad/*`, `three`, `lucide-react`, and `@velipso/polybool` from the root `package.json`, keeping them exclusively in `frontend/package.json`.
