# 15. Production Readiness & DevOps Audit
**Project:** RebarOptima SaaS Platform  
**Audit Date:** November 2026  
**Auditor:** Principal Software Architect & DevOps Lead  
**Scope:** Deployment configuration, containerization, environment variable management, database resiliency, health probes, monitoring, logging, and recovery protocols.

---

## 1. Executive Summary

RebarOptima is **NOT currently ready for production deployment**. While individual frontend pages render and development dev servers run smoothly, the production deployment infrastructure contains severe architectural risks that can lead to **silent data loss**, **unauthenticated access**, and **container downtime**:
1. **Silent Fallback to In-Memory Database:** If MongoDB Atlas connection drops or environment variables are misconfigured, the backend does not terminate or raise an alert. It silently defaults to an ephemeral in-memory dictionary.
2. **False-Positive Health Check (`/api/health`):** The healthcheck probe returns HTTP 200 OK even when running in in-memory fallback mode, preventing Kubernetes or Docker health monitors from restarting the unhealthy instance.
3. **Docker Compose Environment Variable Disconnect:** `docker-compose.yml` provides `DATABASE_URL`, whereas `main.ts` expects `MONGODB_URI`. Deploying with standard compose boots into ephemeral in-memory storage immediately.
4. **Hardcoded Insecure Secrets:** Fallback JWT secrets (`'fallback-access-secret'`) allow token generation without valid environment configuration.
5. **No Production Process Supervisor or Clustering:** Single Node.js thread; unhandled CPU spikes in the optimizer freeze all requests.

## 2. Infrastructure & Deployment Analysis

### 2.1 Container Configuration (`backend/Dockerfile` & `docker-compose.yml`)

#### Dockerfile Analysis:
```dockerfile
# Multi-stage build with node:22-bookworm-slim
RUN apt-get update && apt-get install -y --no-install-recommends \
    libredwg-tools \
    xvfb \
    ca-certificates
```
- **Strengths:** Installs `libredwg-tools` and `xvfb` for headless DWG to DXF conversion.
- **Weaknesses:**
  - Runs as the root user (`USER root` default). Container security best practices mandate running as a non-privileged `node` user.
  - `CMD ["node", "dist/main.js"]` does not handle `SIGINT`/`SIGTERM` gracefully, preventing clean database disconnection during rolling updates.

#### Docker-Compose Environment Mismatch (Confirmed P0 Defect):
```yaml
# backend/docker-compose.yml (Lines 21-26)
environment:
  - DATABASE_URL=mongodb://mongodb:27017/rebar_optima
  - REDIS_HOST=redis
  - REDIS_PORT=6379
```
```typescript
// backend/src/main.ts (Line 282)
const uri = process.env.MONGODB_URI; // DATABASE_URL is completely ignored!
```
- **Result:** Running `docker compose up` spins up MongoDB on port 27017, but the API never connects to it because it reads `process.env.MONGODB_URI` (which is undefined). It drops directly into `InMemoryDb`.

## 4. Top Production Risks

### Risk 1: The "Silent Data Wipe" Scenario (P0)
1. In production, a transient network blip occurs between the cloud VM and MongoDB Atlas.
2. `connectDB()` hits `serverSelectionTimeoutMS: 10000`.
3. Catch block catches error and logs: `⚠️ Could not connect to MONGODB_URI. Falling back to In-Memory DB`.
4. Load balancer queries `GET /api/health` -> gets `200 OK` (with `database.connected: false`).
5. Application continues accepting customer orders, casting logs, and attendance check-ins.
6. The container restarts or scales down overnight.
7. **All customer transactions written during that window disappear permanently.**

### Risk 2: Denial of Service via Optimizer CPU Starvation (P1)
- A project engineer runs a cutting stock optimization for 2,000 rebar pieces.
- Because `solve1DCSP` executes synchronously on the main thread without worker threads or a background BullMQ queue, Node's event loop blocks for 10–30 seconds.
- During this window, all health probes time out, Socket.IO pings fail, and ingress proxies drop active connections.

### Risk 3: Stale Asset Caching on Frontend (P2)
- Frontend Vite configuration produces assets in `dist/assets/`.
- Without explicit Cache-Control headers (`no-cache` on `index.html`, immutable hash on `.js` chunks), users in production frequently receive mismatched chunk errors following redeployments.

## 5. Required Steps Prior to Production Release

1. **Fail-Fast Database Initialization:** Remove `InMemoryDb` from production builds entirely. If MongoDB cannot be reached after 3 retries, the server must terminate (`process.exit(1)`).
2. **Correct `/api/health` Status Codes:** Return HTTP 503 Service Unavailable if `db === null` or Atlas is disconnected.
3. **Standardize Environment Variables:** Align `docker-compose.yml` and `.env.example` to use `MONGODB_URI` consistently.
4. **Enforce JWT Secrets:** Throw a fatal error on boot if `process.env.JWT_ACCESS_SECRET` is unset or equals the default fallback string.
5. **Implement Worker Threads for Optimizer:** Move 1D-CSP bin packing calculations off the main Express event loop.
