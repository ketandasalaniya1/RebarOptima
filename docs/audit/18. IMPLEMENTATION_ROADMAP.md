# 18. Implementation Roadmap (Recommendation Only)
**Project:** RebarOptima SaaS Platform  
**Audit Date:** November 2026  
**Auditor:** Principal Software Architect & Technical Lead  
**Scope:** Phased, safe, non-destructive implementation roadmap to remediate all identified issues without breaking working functionality.

---

## 1. Guiding Principles & Safety Protocols

In accordance with the **Golden Rule** of RebarOptima:
1. **Zero Downtime / Zero Data Loss:** Every change must preserve existing customer records and backwards compatibility.
2. **Smallest Safe Change:** Changes are rolled out incrementally in 4 distinct phases.
3. **No Blind Rewrites:** Working business logic is guarded by regression tests before refactoring.
4. **Vibe Coding Friendly:** Clear step-by-step milestones with explicit acceptance criteria.

---

## 2. Four-Phase Implementation Roadmap

```
Phase 1: Zero-Risk Stabilization & Critical Security (Days 1–5)
  ├── P0 Fixes: JWT Fallback Removal, Silent In-Memory Removal, Docker Compose Alignment
  ├── Critical Integrity: Batch Deletion Rollback Compensation
  └── Mathematical Accuracy: Optimizer Kerf & Trim Formula Corrections

Phase 2: Data Integrity & Architectural Standardization (Weeks 2–3)
  ├── Database Standardization: BSON ObjectId enforcement, Compound Indexes
  ├── Project Isolation: Universal Redux Epoch Hook for Submodules
  ├── High-Throughput Safety: Multi-Document MongoDB Session Transactions
  └── Optimizer Concurrency: Node Worker Threads for 1D-CSP solver

Phase 3: Duplication Consolidation & Code Cleanliness (Weeks 4–5)
  ├── BBS Consolidation: Retiring legacy BBSPage in favor of Phase 2 BBS Wizard
  ├── Block Entity Unification: Migrating 5 duplicate collections into canonical project_blocks
  ├── Backend Router Extraction: Splitting 3,466-line main.ts into modular router files
  └── Dependency Cleanup: Evicting Vue 3 / Element Plus and dead NestJS stubs

Phase 4: Frontend Modernization, Observability & Production Go-Live (Weeks 6–7)
  ├── Frontend Code Splitting: React.lazy() route chunks and React Router migration
  ├── Testing Suite: Vitest for frontend and integration harness for engineering logic
  ├── Observability: Winston/Pino structured logging, accurate /api/health probes
  └── Final Production Hardening & CI/CD Pipeline
```

## 3. Phase 1: Critical Stabilization & Security (Immediate — P0 Issues)

### Task 1.1: Prevent Silent Data Loss & Fail-Fast Database Boot
- **Target Issues:** `REB-P0-002`, `REB-P0-003`, `REB-P0-006`
- **Affected Files:** `backend/src/main.ts`, `backend/docker-compose.yml`
- **Action:**
  1. Remove `InMemoryDb` fallback in production mode. If `client.connect()` fails, retry 3 times with exponential backoff; if unsuccessful, exit process with code 1.
  2. Update `docker-compose.yml` environment variable from `DATABASE_URL` to `MONGODB_URI`.
  3. Update `/api/health` to return HTTP 503 if database connection is inactive.
- **Risk:** Low (prevents silent data corruption).
- **Acceptance Criteria:** Starting the server without MongoDB causes immediate exit; `/api/health` accurately reflects database reachability.

### Task 1.2: Enforce JWT Secret Injection
- **Target Issues:** `REB-P0-004`
- **Affected Files:** `backend/src/main.ts`
- **Action:** Remove `'fallback-access-secret'`. Add startup assertion: `if (!process.env.JWT_ACCESS_SECRET) throw new Error("FATAL: JWT_ACCESS_SECRET required");`.
- **Risk:** Low (zero impact on valid installations with `.env`).
- **Acceptance Criteria:** Server refuses to start if `JWT_ACCESS_SECRET` is undefined or set to default fallback.

### Task 1.3: Safe Batch Deletion with Compensatory Inventory Reversal
- **Target Issues:** `REB-P0-005`
- **Affected Files:** `backend/src/main.ts:1673`
- **Action:** Refactor `DELETE /api/batches/:id` to execute within a MongoDB session:
  1. Identify master steel bars allocated to the batch and restore their stock quantities.
  2. Delete or mark generated remnant items as invalid in the remnant collection.
  3. Append an offsetting compensatory entry to `steel_ledger`.
  4. Soft-delete the batch record (`status: 'cancelled'`).
- **Risk:** Medium (touches inventory ledger).
- **Acceptance Criteria:** Deleting a batch completely restores physical steel bar stock and invalidates child remnants.

### Task 1.4: Optimizer Mathematical Correction (Kerf & Trim)
- **Target Issues:** `REB-P1-012`, `REB-P1-013`
- **Affected Files:** `backend/src/batches/optimizer.engine.ts`
- **Action:**
  1. Change kerf calculation from `parts.length * kerf` to `Math.max(0, parts.length - 1) * kerf`.
  2. Apply trim margin deduction only once per stock bar, not twice on remnants.
- **Risk:** Very Low (fixes inaccurate waste calculation).
- **Acceptance Criteria:** Cutting a 12m bar into two 6m pieces with 3mm kerf correctly accounts for exactly 1 cut (3mm loss).

## 4. Phase 2: Data Integrity & Architectural Standardization (High Priority)

### Task 2.1: Database Schema & Index Standardization
- **Target Issues:** `REB-P1-007`, `REB-P2-006`
- **Affected Files:** All backend router queries and MongoDB models.
- **Action:**
  1. Standardize query lookup helpers: create a robust `toMongoId(id)` helper that gracefully handles valid 24-character hex strings and BSON `ObjectId`.
  2. Add compound indexes via database migration script:
     - `attendance_records`: `{ companyId: 1, projectId: 1, date: -1 }`
     - `inventory_transactions`: `{ companyId: 1, projectId: 1, createdAt: -1 }`
     - `chat_messages`: `{ channelId: 1, createdAt: 1 }`
- **Risk:** Low (indexes are non-destructive).
- **Acceptance Criteria:** Query latency on 10,000+ attendance records drops below 20ms; explain plan shows `IXSCAN`.

### Task 2.2: Universal Project Context Subscription in Submodules
- **Target Issues:** `REB-P1-003`, `REB-P1-011`
- **Affected Files:** `frontend/src/store/slices/projectSlice.js`, `frontend/src/hooks/useActiveProject.js`, all page components.
- **Action:**
  1. Standardize `localStorage` key to `rebar_active_project_id`.
  2. Ensure `useActiveProject()` exposes `projectEpoch`. Add `projectEpoch` to `useEffect` dependency arrays across all submodules (Attendance, Casting, BBS, Inventory).
- **Risk:** Low (fixes stale project data).
- **Acceptance Criteria:** Switching projects in the top navigation bar updates all open tabs and pages immediately without requiring browser reload.

### Task 2.3: Offload Optimizer Calculations to Worker Threads
- **Target Issues:** `REB-P1-015`
- **Affected Files:** `backend/src/batches/optimizer.worker.ts`, `backend/src/main.ts`
- **Action:** Wrap `solve1DCSP` in a Node.js `worker_threads` executor pool, keeping the main Express event loop responsive to incoming HTTP/WebSocket traffic.
- **Risk:** Medium (requires thread pool handling).
- **Acceptance Criteria:** Running a 1,000-piece optimization does not cause healthcheck timeouts or WebSocket disconnects.

## 5. Phase 3: Duplication Consolidation (Medium Priority)

### Task 3.1: Consolidate BBS Modules
- **Target Issues:** `REB-P1-001`, `REB-P2-009`
- **Affected Files:** `frontend/src/pages/BBSPage/`
- **Action:**
  1. Designate `BBSWizard.jsx` as the canonical Bar Bending Schedule generator.
  2. Route all legacy BBS links to the wizard.
  3. Standardize bend deductions to IS 2502 / BS 8666 tables.
- **Risk:** Low (legacy code preserved until user verification).
- **Acceptance Criteria:** Single entry point for BBS creation with consistent rebar schedule calculations.

### Task 3.2: Unify Disparate Block/Wing Collections
- **Target Issues:** `REB-P1-005`
- **Affected Files:** `backend/src/projects/project-blocks.service.ts`, database collections.
- **Action:**
  1. Create a non-destructive data migration script copying unique blocks from `casting_blocks`, `bbs_blocks`, and `crm_blocks` into `project_blocks`.
  2. Update casting and BBS services to read from `project_blocks`.
- **Risk:** Medium (requires backward-compatible reads during rollout).
- **Acceptance Criteria:** Creating or renaming a block in Project Settings is immediately reflected in Casting, CRM, and BBS dropdowns.

### Task 3.3: Decompose `main.ts` into Feature Routers
- **Target Issues:** `REB-P1-006`, `REB-P2-003`
- **Affected Files:** `backend/src/main.ts`, `backend/src/batches/batches.routes.ts`, `backend/src/inventory/inventory.routes.ts`
- **Action:** Extract inline route handlers from `main.ts` into existing dedicated route modules. Keep `main.ts` under 200 lines strictly as the application bootstrapper.
- **Risk:** Low (routing contracts remain 100% identical).
- **Acceptance Criteria:** All API endpoints respond identically; `main.ts` reduced from 3,466 lines to < 200 lines.

### Task 3.4: Evict Vue 3 & Dead NestJS Packages
- **Target Issues:** `REB-P2-001`, `REB-P2-015`, `TD-ARCH-02`
- **Affected Files:** `frontend/package.json`, `backend/package.json`, `package.json`
- **Action:**
  1. Remove Vue 3, Element Plus, and VueUse dependencies from `frontend/package.json`.
  2. Remove dead `@nestjs/*` framework dependencies from `backend/package.json`.
  3. Deduplicate root `package.json`.
- **Risk:** Low (after verifying CADViewer does not rely on Vue runtime).
- **Acceptance Criteria:** `npm install` runs 40% faster; node_modules footprint reduced by over 150MB.

## 6. Phase 4: Modernization, Testing & Production Go-Live

### Task 4.1: Frontend Lazy-Loading & Code Splitting
- **Target Issues:** `REB-P2-002`, `REB-P2-012`
- **Affected Files:** `frontend/src/App.jsx`
- **Action:** Convert eager module imports into `React.lazy(() => import('./pages/...'))` wrapped in `Suspense`.
- **Risk:** Low.
- **Acceptance Criteria:** Initial bundle size drops from >4MB to <800KB; Lighthouse performance score improves from ~50 to >85.

### Task 4.2: Frontend Unit & Integration Test Suite
- **Target Issues:** `REB-P2-013`
- **Affected Files:** `frontend/vitest.config.js`, `frontend/src/**/*.test.jsx`
- **Action:** Setup Vitest with React Testing Library. Write comprehensive test suites for:
  - Redux project slice and project switcher.
  - BBS shape calculation formula validators.
  - Cutting optimizer input forms.
- **Risk:** Zero (test-only additions).
- **Acceptance Criteria:** Automated CI runs frontend unit tests with >70% coverage on core business logic.
